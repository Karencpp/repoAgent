# ADR-002：窄仓库工具、统一结果契约与显式执行授权

- 状态：Accepted
- 日期：2026-07-31
- 模块：Restricted repository tools

## 背景

代码维护 Agent 需要查看文件、搜索符号、理解 Python 结构并运行测试。最直接的实现是给模型一个 `shell(command)`，但这会把命令构造、路径范围、参数解析和执行风险同时交给概率模型，也很难对单个能力做权限、超时和评测。

Function Calling 中模型只生成调用意图，真正的工具选择校验、执行与结果回传由 Host 完成。因此工具层必须先提供稳定、窄且可审计的领域契约。

## 决策

第一版只提供五个仓库工具：

| 工具 | 能力 | 风险等级 |
| --- | --- | --- |
| `list_files` | 有限深度和数量的文件树 | 只读 |
| `search_code` | 有限文件大小的精确文本搜索 | 只读 |
| `read_file_range` | 有限行数和字符数的局部读取 | 只读 |
| `inspect_python` | 通过 AST 获取导入和符号结构 | 只读，不执行模块 |
| `run_pytest` | 参数数组方式运行 pytest | 执行目标项目代码 |

具体约束：

1. 所有文件路径通过当前 `ProjectContext` 解析，不接受仓库外路径。
2. 不暴露任意 Shell 字符串。
3. 子进程使用参数数组、固定 cwd、`shell=False`、超时和输出上限。
4. pytest target 必须先解析成仓库内真实路径，不允许以选项前缀开头。
5. pytest 默认拒绝执行；上层必须显式设置代码执行授权。
6. AST 工具只解析源码，不 import 或执行目标模块。
7. 所有工具使用统一 `ToolResult`，错误具有稳定 kind、retryable 和 details。
8. pytest 非零退出码属于有效 Observation，而不是工具基础设施错误。
9. Graph 只依赖 `RepositoryToolPort`，后续 Local 与 MCP Adapter 可替换。

## 为什么测试失败不是工具失败

执行 `pytest` 后出现断言失败，说明：

- 进程正常启动；
- pytest 正常收集和运行；
- 工具成功返回了对 Agent 很有价值的失败证据。

因此此时 `ToolResult.status=success`，同时 `tests_passed=false`、`exit_code!=0`。只有超时、无法启动、权限拒绝等情况才是工具错误。

如果混淆二者，Agent 可能对稳定失败进行无意义的基础设施重试，而不是进入 Reflection 分析代码。

## 为什么 AST 工具不直接 import 模块

import 会执行模块顶层代码，可能触发网络、文件写入、环境检查或任意副作用。AST 可以在不执行代码的情况下得到类、函数、限定名称、装饰器、导入和行号，适合第一阶段代码定位。

AST 的局限是不能完全还原动态导入、运行时猴子补丁、反射和框架生成关系。

## 为什么 pytest 需要独立授权

文件路径沙箱只能限制工具显式读取的文件。pytest 会执行目标项目代码，项目代码仍可能访问网络、环境变量和仓库外文件。因此“目标位于 repo_root 内”不等于“执行安全”。

当前实现只建立应用层授权边界。若要更强隔离，需要容器、受限账户、文件系统挂载、网络策略和资源配额。

## 没有选择的方案

### 通用 Shell 工具

表达能力强，但权限面过大、Schema 过弱、审计粒度粗，也难区分不同操作的副作用，因此拒绝。

### 一开始全部通过 MCP

MCP 是协议适配层，不应替代领域契约。先稳定 Local Port 和行为测试，后续 MCP Server/Adapter 复用同一语义。

### 直接执行用户提供的 pytest 参数列表

即使使用 `shell=False`，任意 pytest 插件和参数仍可能扩大行为。第一版只允许 targets、`-k`、最大失败数、超时和输出上限，并由程序构造其余参数。

### 搜索时立即依赖 ripgrep

ripgrep 性能更强，但会增加外部可执行文件依赖和 JSON 解析分支。当前小型项目先用受控 Python 搜索建立语义与测试；大型仓库可在保持 Port 不变的情况下替换实现。

## 代价与局限

- Python 搜索不适合超大型仓库，且当前仅按文件大小跳过大文件。
- 文本读取使用 UTF-8 容错解码，可能把二进制内容转换成噪声。
- pytest 使用当前 Python 解释器，尚未解析目标项目自己的虚拟环境。
- 代码执行授权不是 OS 沙箱；授权后项目代码仍有系统权限。
- 当前输入是内部 dataclass，模型侧 JSON Schema 和 Pydantic 适配将在 Agent/Tool Registry 模块完成。
- 进程 stdout、stderr 各自应用输出上限，总输出可能接近两倍配置值。

## 验证证据

测试覆盖：

- 忽略缓存和虚拟环境目录；
- glob、深度和结果数量限制；
- 搜索路径、行号、列号与大小元数据；
- 空查询和危险 glob；
- 局部读取与字符截断；
- 仓库外路径拒绝；
- AST 导入、类、方法、异步函数、符号过滤和语法错误；
- pytest target 规范化与仓库外 target 拒绝；
- pytest 执行授权；
- 测试失败与工具失败语义分离；
- 超时保留部分输出并标记可重试；
- 子进程输出头尾截断。

## 未来切换条件

- 大型仓库：将搜索实现替换为 ripgrep 或代码索引服务。
- 执行不可信代码：加入容器/沙箱执行器。
- 多语言仓库：增加语言专用结构分析器，并保持 Port 层统一。
- 接入 LLM：增加 Pydantic/JSON Schema Tool Registry 和原始参数验证边界。
- 接入 MCP：实现 `MCPRepositoryTools`，并用契约测试保证与 Local 实现一致。
