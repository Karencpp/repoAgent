# ADR-003：结构化 Tool Registry 与最小 ReAct Runtime

- 状态：Accepted
- 日期：2026-07-31
- 模块：Tool Registry and ReAct Runtime

## 背景

上一模块已经有五个受限仓库工具，但工具仍以 Python 方法存在，模型不知道有哪些工具、参数长什么样，Host 也没有统一的模型参数校验和循环控制。

代码维护任务通常不能一次模型调用完成。模型需要先搜索或读取代码，根据 Observation 决定下一步，最终在证据足够时回答。这要求一个可测试的控制循环，而不只是把工具描述塞进 Prompt。

## 决策

### 1. 使用 Pydantic 建立模型输入边界

每个仓库工具增加一份面向模型的 Pydantic 参数模型。注册表从模型生成 JSON Schema，并在分发前执行严格校验：

- 禁止额外字段；
- 限制字符串、数量、行范围和超时；
- 拒绝危险 glob、空白查询和伪装成 pytest 选项的 target；
- 校验通过后再转换成工具层 dataclass。

Pydantic 模型属于“不可信 JSON → 可信领域请求”的适配层，原有 dataclass 仍是工具内部契约。

### 2. Tool Registry 同时负责发现、过滤、校验和分发

每个注册项包含：

- 工具能力与风险元数据；
- 参数模型；
- 实际处理函数。

Registry 对模型暴露名称、描述、JSON Schema、访问类型和执行风险；调用时再检查工具是否存在、是否在本次任务白名单中，并把异常转成统一 ToolResult。

工具白名单既过滤模型看到的工具，又在 dispatch 时二次校验。只做前者不安全，因为模型输出本身不可信。

### 3. 模型只返回两种结构化决策

决策使用带 `type` 判别字段的联合类型：

- `tool_call`：工具名、参数、简短决策摘要；
- `final_answer`：最终答案、简短决策摘要。

原始模型响应必须经过本地 Schema 校验。调用失败或结构不合法统一转为 ModelDecisionError。

系统不要求、保存或展示模型的完整隐藏思维链，只保存面向审计的 `decision_summary`。可解释性来自输入、工具调用、Observation、状态迁移和停止原因，而不是依赖不可验证的长篇推理文本。

### 4. ReAct Runtime 由 Host 确定性控制

每轮执行：

1. Host 组装目标、工具定义、历史 Observation 和剩余预算；
2. 模型返回一个结构化决策；
3. 若为最终答案则结束；
4. 若为工具调用，Host 检查预算和重复调用；
5. Registry 校验并执行工具；
6. ToolResult 写入事件，再作为下一轮 Observation；
7. 继续直到完成或触发停止条件。

Runtime 设置四类确定性约束：最大迭代数、最大工具调用数、连续工具错误上限、完全相同调用上限。

### 5. 使用脚本模型进行确定性测试

ScriptedDecisionClient 按预设顺序返回决策并记录 ModelRequest。测试不依赖网络、模型价格、随机性或供应商，可精确验证第二轮是否拿到了上一轮 Observation，以及各停止条件是否正确。

## ReAct 与 Function Calling 的关系

ReAct 是“决策—行动—观察—再决策”的控制模式；Function Calling 是模型表达某次工具调用意图的结构化协议。当前实现用 Function Calling 风格的数据结构承载 ReAct 的 Action，由 Host 完成真实执行和循环控制。

二者不是互斥选型，也不能把模型能输出 tool call 误认为已经拥有完整 Agent Runtime。

## 没有选择的方案

### 自由文本解析工具调用

需要从自然语言中提取工具名和参数，歧义大且错误难分类，因此拒绝。

### 只依赖模型供应商的 Schema 保证

供应商约束可以降低格式错误，但本地边界仍需防御模型错误、版本差异、测试替身和外部调用，因此必须再次校验。

### 立即引入 LangGraph

本模块先把单个执行循环的输入、输出、事件和停止语义做成普通 Python。这样能单测核心行为，也能明确未来 Graph Node 封装的对象。LangGraph 更适合后续承载 Plan、Execute、Evaluate、Reflect 的外层状态机，不替代工具分发和 ReAct 内部约束。

### 把完整思维链写入 Trace

长篇内部推理既不稳定，也不应成为系统正确性的依赖。Trace 记录简短决策摘要、结构化动作、外部观察、预算和停止原因即可审计。

## 代价与局限

- Pydantic 参数模型与内部 dataclass 存在少量字段重复，需要契约测试防止漂移。
- 目前没有接真实 LLM，仅提供供应商无关接口和脚本测试模型。
- Observation 当前全部累积，长任务尚未做摘要、裁剪和上下文窗口管理。
- 重复检测只识别工具名和参数完全相同的调用，不能识别语义等价循环。
- Runtime 是同步串行执行，尚未处理并行工具、取消和流式事件。
- 相同读取在仓库版本变化后可能有意义；未来写工具加入后，指纹应结合项目 revision 或状态版本。

## 验证证据

模块测试覆盖：

- JSON Schema 和工具风险元数据；
- 模型可见工具过滤与 dispatch 二次权限检查；
- 非法、额外参数拒绝；
- 有效参数转换和真实工具调用；
- 非法模型决策拒绝；
- Action → Observation → 下一轮决策；
- 工具错误作为可恢复 Observation；
- 连续工具错误、重复调用、工具预算和迭代预算停止；
- 仅向模型暴露任务允许的工具；
- 脚本模型返回强类型决策。

全项目当前 46 个测试通过。

## 未来切换条件

- 接真实模型：实现 RawDecisionClient 供应商适配器，不改变 Runtime。
- 进入多阶段工作流：把 ReActExecutor 封装成 LangGraph Execute Node。
- 长上下文：给 Observation 增加保真摘要、证据引用和裁剪策略。
- 引入写工具：把项目 revision、变更集和幂等键纳入循环检测。
- 并行工具：增加任务组、结果排序、取消与总预算规则。
