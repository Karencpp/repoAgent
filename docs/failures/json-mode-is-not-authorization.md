# 失败案例：把 JSON 模式当成授权边界

## 现象

模型返回了一段语法正确的 JSON：

```json
{
  "type": "tool_call",
  "tool_name": "shell",
  "arguments": {"command": "..."},
  "decision_summary": "需要执行命令"
}
```

系统因为 JSON 可以解析，就直接寻找并执行同名函数。

## 根因

混淆了四个层次：

1. JSON 语法合法；
2. 数据满足领域 Schema；
3. 工具确实在注册表中；
4. 当前步骤和用户授权允许调用。

JSON 模式最多改善第一层。模型仍可能编造工具名、遗漏字段、给出危险参数，或者受到仓库文本中的 Prompt injection 影响。

## 当前处理

- 供应商响应先做协议和 JSON 解析；
- Pydantic 校验判别联合类型；
- Planner 检查所有 `allowed_tools` 都已注册；
- ReAct 只接收当前步骤白名单；
- Tool Registry 在执行前再次检查工具存在性、白名单、参数 Schema 和显式授权；
- 工具层继续执行路径沙箱和进程限制。

## 面试结论

结构化输出解决的是“机器能否稳定读取模型提议”，不是“提议是否可信或获授权”。LLM 永远位于权限边界之外，真正的执行授权必须由确定性 Host 代码掌握。
