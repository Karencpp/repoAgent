# 模块 02 面试讲解：受限仓库工具与 Function Calling

## 30 秒回答

我没有给模型开放任意 Shell，而是把仓库能力拆成文件树、精确搜索、局部读取、AST 分析和 pytest 五个窄工具。模型只生成工具名和参数，Host 负责 Schema、权限和路径校验，再通过 RepositoryToolPort 执行。所有工具返回统一 ToolResult，区分参数、权限、解析、超时和执行错误。pytest 非零退出码是有效测试 Observation，不是工具错误；同时由于 pytest 会执行项目代码，默认必须经过显式执行授权。

## 2 分钟回答

Function Calling 并不是模型直接执行函数。Host 先把工具描述和输入结构交给模型，模型输出调用意图，Host 再做参数校验、权限校验和真实执行，最后把结果作为 Observation 返回 Agent。

最简单的代码维护工具是 `shell(command)`，但它把权限面和参数空间做得过大，也很难对搜索、读取和执行测试设置不同策略。所以我拆成五个窄工具。所有文件操作都通过上一模块的 ProjectContext，先解析真实路径再确认没有越过 repo root；结果还会携带行号、截断和上限信息，防止模型把不完整结果当完整事实。

Python 结构分析用 AST 而不是 import，因为 import 会执行模块顶层代码。pytest 使用参数数组和 `shell=False`，并设置固定 cwd、超时和输出头尾截断。不过路径沙箱不等于进程沙箱，pytest 仍能执行任意项目代码，所以默认关闭，只有上层明确授权才运行。

结果语义上，我把工具是否成功和业务是否成功分开。测试断言失败意味着工具成功提供了失败证据，应交给 Reflection；进程超时或无法启动才进入工具错误分支。Graph 依赖 RepositoryToolPort，未来切 MCP 不需要改节点语义。

## 必须理解的调用边界

```text
LLM：选择工具并生成参数
Host：校验、授权、路由、执行和记录 Trace
Tool：读取环境或执行窄能力
Observation：工具返回给 Agent 的结构化外部事实
```

## 面试官可能追问

### Function Calling 时到底是谁执行函数？

模型只返回结构化调用意图。Host 或 Agent Runtime 找到对应工具、校验参数并执行真实函数，然后把结果加入下一轮模型上下文。

### 为什么不能只靠 System Prompt 说“不要执行危险命令”？

Prompt 是概率约束，不能替代程序权限。模型可能误解、被工具输出注入或生成错误参数。路径、工具白名单、超时和审批必须由确定性代码执行。

### 为什么窄工具比 Shell 更好？

窄工具有明确 Schema、副作用、超时、返回结构和评测指标。Shell 只有一个字符串参数，几乎把所有能力和风险合并在一起。

### search_code 和 RAG 是不是重复？

不是。search_code 解决函数名、错误码、路径等精确匹配；RAG 解决设计文档和自然语言的语义召回。代码搜索结果带行号，更适合成为可验证 Evidence。

### 为什么用 AST，不用正则？

正则无法可靠区分类、嵌套函数、异步函数、装饰器和多行签名。AST 利用语言语法结构，并且不会执行代码。

### AST 能解决完整调用图吗？

不能。动态分派、反射、依赖注入和猴子补丁需要类型分析或运行时信息。当前 AST 工具定位定义和导入，不宣称完成完整静态分析。

### pytest 返回 1 为什么 ToolResult 还是成功？

因为工具基础设施正常完成，失败断言是业务观察。这个结果应触发 Reflection，而不是基础设施重试。

### 哪些错误可以重试？

临时超时可以在缩小范围或调整预算后有限重试；参数错误应修正参数；权限错误不能自动重试；确定性的测试失败应修改代码或计划。

### 为什么输出截断要保留头尾？

输出头部通常包含命令、收集阶段和环境信息，尾部通常包含最终异常和摘要。只保留一端容易丢失诊断关键点。截断标记还必须显式告诉模型内容不完整。

### `shell=False` 是否等于安全？

不是。它只避免 Shell 对字符串进行二次解释。被启动的 pytest/Python 仍可以执行任意项目代码，所以还需要授权和真正的进程隔离。

### 为什么默认不允许运行 pytest？

读取源码与执行源码风险不同。执行目标项目代码必须是显式能力，未来由用户请求范围或 Human-in-the-loop 节点授予。

### RepositoryToolPort 的意义是什么？

让 Graph 依赖领域语义，而不是本地函数或 MCP 协议细节。Local、MCP 和测试替身可以实现同一 Port，并通过契约测试保证一致。

### 为什么当前搜索不用 ripgrep？

第一版先用 Python 实现固定语义和测试，减少外部依赖。大型仓库达到性能瓶颈时，可以在不改变 Port 的情况下换成 ripgrep 或索引服务。

## 当前代码证据

- `tools/models.py`：ToolResult、ToolErrorKind、ProcessResult。
- `tools/schemas.py`：五个工具的结构化输入输出。
- `tools/catalog.py`：能力、副作用和授权元数据。
- `tools/repository.py`：本地工具、路径和参数约束。
- `tools/process.py`：无 Shell 子进程、超时与输出截断。
- `tools/port.py`：Graph 依赖的工具端口。
- `tests/test_repository_tools.py`：16 个工具层测试。

加上模块一测试，当前总计 32 个测试全部通过。

## 主动说明的局限

1. 搜索实现还未针对大型仓库优化。
2. UTF-8 容错读取还没有完整二进制检测。
3. pytest 使用当前解释器，未自动选择项目虚拟环境。
4. 显式授权不是容器或 OS 沙箱。
5. 模型侧 JSON Schema 和 Tool Registry 尚未接入。
6. MCP Adapter 尚未实现，目前只有稳定 Port。

这些局限分别对应后续的 Tool Registry、LangGraph、MCP 和隔离执行模块。
